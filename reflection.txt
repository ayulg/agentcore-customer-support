Design Decision: I chose to implement the refund tool using a direct boto3 invocation with a custom ClientContext header, rather than relying solely on the AgentCore Gateway's MCP path. This decision was driven by a sandbox IAM constraint that prevented modifying the Gateway execution role's trust policy. By base64-encoding a ClientContext containing bedrockAgentCoreToolName, the direct Lambda invocation mimics exactly what the Gateway does when it routes tools — the handler splits on "___" and extracts the bare tool name. This pattern preserves the Lambda's routing logic while allowing the agent to reach it without the Gateway. The same approach was applied to order tracking via a direct HTTP call to API Gateway, which combined with the Gateway MCP path provides redundant access to backend systems.

Challenge: The most significant challenge was diagnosing the MCPClientInitializationError "the client session is not running" error that surfaced when the agent tried to call Gateway tools. CloudWatch logs revealed the tool was being invoked after the with mcp_client: context block had already exited, tearing down the async transport. Even restructuring the code to keep the agent call inside the context still produced the error, indicating deeper issues with how Strands' MCPClient manages its background thread across the Agent's async execution context. I resolved this by adding direct boto3-based tools for order tracking and refund processing that bypass the MCP layer entirely, while keeping the Gateway connection attempt wrapped in try/except for graceful degradation. I also discovered that AgentCore Memory requires 60-90 seconds after a session ends to perform semantic extraction before memories become retrievable — a timing detail not obvious from the documentation.

Production Consideration: From a security standpoint, the NONE authorizer on the Gateway was necessary for this educational project but would be unacceptable in production — any caller with the URL could invoke order-tracking and refund operations without credentials. A production deployment would require IAM SigV4 signing on inbound requests plus per-customer authorization to prevent enumeration attacks on the REST API (e.g., preventing customer A from querying customer B's orders by guessing order IDs). I would also add CloudWatch alarms on the runtime's Lambda invocation rate to detect anomalous refund activity, since refund processing is a high-value operation that fraudsters often target, and I would cache frequently-requested knowledge base lookups in DynamoDB to reduce Bedrock Retrieve API costs at scale.
